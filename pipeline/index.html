Pipeline

From public archives to joined tables in four stages. Each stage lives in its own repository; the formats passed between them are the contract.

data-gathering  →  data-cleaning  →  PostgreSQL linuxkernel  →  data-matching
 (raw archives)    (clean, load)      (one database, PG18)       (people, employers, links)

  1. Gathering

data-gathering holds one collector per source: commits from the mainline git tree, email from lore.kernel.org, the older FTP and Usenet archives, Marc and Indiana mirrors, Bugzilla, and the MAINTAINERS history. A file-tree collector turns each release into the filegraph dependency graph.

lore.kernel.org now sits behind a proof-of-work wall, so a re-crawl has to use the git protocol, not HTTP.

  1. Cleaning and loading

data-cleaning imports raw collections into MongoDB for inspection, cleans them, and exports them to PostgreSQL. The loaders are parallel and idempotent, and a commensurability check proves that a refactor produces byte-identical output before a full load.

  1. The database

postgres-mainteneance records every operation on the database: the PostgreSQL 15 → 18 migration, the consolidation of two email schemas into mails, de-duplication, and the rebuild manifests. data-info holds the data dictionary, the authoritative reference for every schema, table and column.

  1. Matching

data-matching resolves entities:

  • Identity resolution collapses the many addresses one developer uses across lists, commits and bug reports into one person, so careers can be followed across employers.

  • Message–commit matching links posted patches to the commits they became.

Verification

None of these repositories has a unit-test suite. Verification happens in the database itself: after any change, meta.assert_all() must pass, stage counts are compared against the documented build record, and the rows are read. Every invariant exists because that exact failure happened once and nothing caught it.
